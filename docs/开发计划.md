### 3.3 当前数据库职责

当前版本以 MySQL 为唯一业务事实源，Redis 尚未接入。

| 数据/能力 | 当前实现 | 说明 |
|---|---|---|
| 账号、角色、农户、场地、设备组合 | MySQL | 业务基础数据 |
| 预约、预约产品、资源锁 | MySQL | 场地/设备按小时唯一约束 |
| 排队、候补、确认 | MySQL | 顺位、状态、预约绑定均在表中 |
| 通知、模板、重试 | MySQL | 站内/短信记录和重试时间 |
| 销售、统计 | MySQL | 指标实时查询，CSV 导出 |
| 操作日志、资质、故障 | MySQL | 可追溯的业务记录 |
| 登录 token | 后端内存 | 后端重启失效，多实例不共享 |
| 验证码、登录失败次数 | 后端内存 | 后端重启清空，多实例不共享 |
| 限流、短信频控 | 未实现 | 目前没有统一限流层 |
| 定时任务 | 单实例执行 | 多实例会重复执行 |
| 区域字典 | MySQL | 全国 3,947 条，供前端一次加载 |

当前限制：

- 只适合单后端实例；
- 后端重启后所有登录用户需要重新登录；
- 多实例部署时验证码、登录锁定和 token 不共享；
- 定时任务没有分布式互斥；
- 登录、验证码、短信、预约提交没有统一限流和防刷；
- 二次验证还没有短时凭证存储。

MySQL 继续负责业务数据和最终一致性；Redis 只承担短期状态、共享状态、计数和互斥，不替代 MySQL 的业务事实源地位。

## 6. 数据库与 Redis 的职责边界

### 6.1 基本原则

1. MySQL 是业务数据唯一事实源，Redis 不保存不可恢复的业务数据。
2. 预约、资源锁、排队、通知、统计、日志的最终状态以 MySQL 为准。
3. Redis 只保存短期状态、共享状态、计数、缓存和互斥锁。
4. 不允许 Redis 与 MySQL 同时作为同一业务数据的双主。
5. Redis 故障时，不能返回错误的业务成功结果；敏感接口应拒绝服务并报警。

### 6.2 能力分工

| 能力 | 主责存储 | 说明 |
|---|---|---|
| 账号、角色、权限 | MySQL | 长期数据 |
| 农户、场地、设备组合 | MySQL | 长期数据 |
| 预约、预约产品 | MySQL | 业务事实 |
| 场地/设备资源锁 | MySQL | 唯一约束保证，Redis 不能替代 |
| 排队记录、顺位、候补状态 | MySQL | 当前以数据库为准 |
| 通知、模板、重试 | MySQL | Redis 不保存通知正文 |
| 销售、统计、日志、资质、故障 | MySQL | 长期数据 |
| 登录 token | Redis | 短期、可过期、多实例共享 |
| 验证码、登录失败次数 | Redis | TTL 自动过期，多实例共享 |
| 接口限流、验证码防刷 | Redis | 原子计数 |
| 短信频控 | Redis | 按手机号/账号/事件计数 |
| 定时任务互斥 | Redis | 防止多实例重复执行 |
| 二次验证 step-up 凭证 | Redis | 短时有效 |
| 幂等键 | Redis | 短期防重复提交 |
| 区域字典缓存 | Redis | 可选，数据库仍为源 |
| 排队 ZSET | Redis | 可选，需基准测试后再做 |

### 6.3 Redis Key 规划

| Key 模式 | 用途 | 建议 TTL |
|---|---|---|
| `auth:token:{token}` | 登录会话 | 8 小时，与 token 一致 |
| `auth:captcha:{captchaId}` | 验证码 | 5 分钟，一次性删除 |
| `auth:fail:{username}` | 登录失败计数 | 15 分钟 |
| `rate:ip:{ip}:{route}:{window}` | IP 接口限流 | 1 分钟窗口 |
| `rate:account:{id}:{action}` | 账号级操作限流 | 1 分钟窗口 |
| `sms:{phone}:{event}:{window}` | 短信频控 | 60 秒/小时/天 |
| `lock:scheduler:{job}` | 定时任务互斥 | 任务周期 + 30 秒 |
| `stepup:{accountId}:{purpose}` | 敏感操作二次验证 | 5 分钟 |
| `idem:{accountId}:{requestKey}` | 重复提交幂等 | 10 分钟 |
| `cache:region:tree` | 区域树缓存 | 1 小时，导入后主动失效 |

### 6.4 Redis 故障策略

| 场景 | 处理 |
|---|---|
| token 无法校验 | 受保护接口返回 503，不降级为匿名访问 |
| 验证码不可用 | 登录接口返回 503，禁止跳过验证码 |
| 限流不可用 | 登录、验证码、短信、预约提交等敏感接口拒绝服务并报警 |
| 短信频控不可用 | 暂停短信发送，站内通知保留 |
| 定时任务锁不可用 | 跳过本轮任务并报警，避免多实例重复执行 |
| 区域缓存不可用 | 回源 MySQL，不影响业务 |
| Redis 重启 | token 失效，用户重新登录；业务数据不受影响 |

## 7. Redis 开发计划

### 7.1 目标

Redis 是部署阶段的基础设施，不是演示阶段的附加组件。目标是：

- 支持后端多实例部署；
- 登录态、验证码、登录锁定跨实例共享；
- 登录、验证码、短信、预约提交有统一限流；
- 定时任务在多实例下只执行一次；
- 为二次验证、幂等、缓存和后续排队优化提供基础；
- 明确 Redis 故障时的降级边界，避免安全降级。

### 7.2 阶段任务

| 编号 | 任务 | 优先级 | 依赖 | 验收标准 |
|---|---|---|---|---|
| R-01 | Redis 环境与配置 | P0 | 部署环境 | Redis 7 可连接，密码/网络隔离，应用配置可覆盖 |
| R-02 | token 迁 Redis | P0 | R-01 | 两个后端实例共享登录态；退出后 token 立即失效；TTL 正确 |

### 7.3 实施顺序


### 7.4 开发约束

- Redis 只做短期状态，不把预约、资源锁、排队最终状态搬到 Redis；
- 资源占用仍以 MySQL 唯一约束为准，Redis 锁只能作为减少冲突的优化；
- 不允许“Redis 写成功、MySQL 写失败”时返回业务成功；
- 所有 Key 必须带业务前缀和 TTL，禁止无过期键；
- 限流和频控使用 Lua 脚本保证原子性；
- 敏感接口在 Redis 故障时拒绝服务，不静默关闭限流；
- Redis 密码、地址通过环境变量注入，不提交仓库；
- 生产 Redis 必须内网访问、启用认证、配置持久化和监控。

### 7.5 验收场景

1. 两个后端实例交替处理请求，登录态、验证码、登录锁定正常；
2. 同一验证码只能使用一次，过期后失效；
3. 登录、验证码、预约提交超限返回 429，正常用户不受影响；
4. 同一手机号短信发送触发频控，站内通知不受影响；
5. 两个实例同时运行定时任务，每轮只执行一次；
6. 敏感操作 step-up 过期后必须重新验证；
7. 同一幂等键重复提交只生成一条预约；
8. Redis 停止后，受保护接口按既定策略拒绝服务，业务数据无脏写；
9. Redis 恢复后，登录态重建、限流恢复，不出现重复任务。

## 8. 关键业务规则

后续开发不得破坏以下规则：

1. **资源锁**
   - 同场地同一小时只能有一条有效预约；
   - 同设备组合同一小时只能有一条有效预约；
   - 以数据库唯一约束兜底，服务层事务处理。

2. **24 小时边界**
   - 开播前 24 小时内不能取消预约；
   - 开播前 24 小时内不能申请调整；
   - 开播前 24 小时内不能加入排队；
   - 候补截止为开播前 24 小时。

3. **排队与预约**
   - 加入排队时同步创建 `queued` 预约；
   - `queue_ticket.booking_id` 绑定该预约；
   - 候补确认复用该预约，分配设备后转 `approved`；
   - 放弃、超时、关闭队列同步取消预约。

4. **设备故障**
   - 报修后整套设备组合转 `maintenance`；
   - 未来已通过预约自动取消并释放资源锁；
   - 发送故障取消通知；
   - 维修完成后恢复 `available`。

5. **数据隐私**
   - 数据统计员只能访问聚合指标和趋势；
   - 明细、导出只给直播管理员和系统管理员；
   - 农户只能看本人预约、排队和统计。

### 9.2 完成定义

一个任务算完成，必须同时满足：

1. 代码可构建；
2. 接口可调通或页面可操作；
3. 验收标准逐条通过；
4. 数据库变更带迁移 SQL；
5. 接口文档同步；
6. 没有提交密钥或真实数据；
7. 测试或负责人能看到证据。
