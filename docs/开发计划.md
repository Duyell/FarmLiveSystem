## 0. 开发人员接手顺序

新开发人员按这个顺序做，不要跳：

1. 读 [文档索引](README.md)、[需求分析](01_需求/08-需求分析-正式版.md)、[接口文档](02_设计/09-接口文档-正式版.md)、[数据库设计](02_设计/08-数据库设计-正式版.md)、[开发规范](03_开发规范/00-开发规范.md)。
2. 按 [README](../README.md) 启动 MySQL、后端和前端，确认 `admin / Admin@123` 能登录并完成首次改密。
3. 在管理端创建测试账号：直播管理员、数据统计员，以及关联农户 `NF2026001` 的农户账号。
4. 先做任务 16–18：区域接口 → 农户/场地 `countyCode` → 前端三级选择 → 回归测试。
5. 再按任务表进入预约、排队、通知、统计、权限、AI，不跨模块同时改。
6. 每个模块按“接口 → 数据库 → 后端 → 前端 → 测试 → 文档”的顺序做，前一步没通，不进入下一步。

### 0.3 代码放在哪

| 内容 | 位置 |
|---|---|
| 后端接口 | `backend/src/main/java/com/farmlive/web/` |
| 登录、令牌、验证码 | `backend/src/main/java/com/farmlive/auth/` |
| 数据库访问 | `backend/src/main/java/com/farmlive/repo/` |
| 请求/返回对象 | `backend/src/main/java/com/farmlive/dto/` |
| 统一响应、异常 | `backend/src/main/java/com/farmlive/common/` |
| 预约、排队等业务逻辑 | 新建 `backend/src/main/java/com/farmlive/service/`，事务写在服务层 |
| 后端测试 | `backend/src/test/java/com/farmlive/` |
| 前端页面 | `frontend/src/views/` |
| 前端接口调用 | `frontend/src/api/` |
| 前端路由 | `frontend/src/router/index.ts` |
| 数据库初始化 | `init.sql` |
| 数据库增量脚本 | `deploy/sql/`，按 `003-模块名.sql` 递增 |

规则：

- 控制器只做参数校验和调用，不写事务；
- 预约、排队、候补的事务和资源锁放在服务层；
- 一个模块一个服务，不把所有逻辑塞进 `AdminController`；
- 前端一个模块一个 `views` 页面，接口统一放 `api`；
- 数据库改动必须同时有初始化脚本和增量脚本。

## 1. 目标

按“先能登录和管数据，再能预约排队，最后做增强和交付”的顺序开发，保证每一步都有可运行、可验收的结果。

当前第一阶段先完成：

- 数据库初始化；
- 登录、退出、修改密码；
- 系统管理员工作台；
- 账号、农户、场地、设备四类数据的增删改查；
- 电脑管理端对应页面。

## 3. 开发原则

1. 先跑通主流程，再做增强。
2. 数据库先定，接口跟着数据库和页面走。
3. 后端接口先能 curl 调通，前端再接。
4. 每个功能有验收标准，没有证据不算完成。
5. 不做微服务、不上消息队列、不上搜索引擎。
6. 代码、SQL、配置分开管理；密钥不进仓库。
7. 先做电脑管理端；手机网页在核心页面完成后适配。

## 7. 依赖关系

```text
数据库
  ↓
后端骨架 → 登录/权限 → 账号管理
  ↓                         ↓
农户/场地/设备 ─────────→ 工作台
  ↓
预约 → 资源占用 → 审核 → 取消
  ↓
排队 → 候补 → 通知
  ↓
调整 → 统计 → 导出
  ↓
知识库 → AI 问答 → 评测
```

- 前端依赖后端接口先调通；
- 预约依赖场地、设备、农户；
- 排队依赖预约和场地；
- 统计依赖完成标记和销售录入；
- AI 依赖知识库文档；
- 部署依赖全部功能。

## 8. 完成标准

一个任务算完成，要同时满足：

1. 代码能构建；
2. 接口能调通，或页面能操作；
3. 验收标准逐条通过；
4. 数据库变更写了 SQL；
5. 接口文档同步；
6. 没有把密钥、真实数据提交到仓库；
7. 测试人员或项目负责人看到证据。

## 10. 变更控制

- 新增需求先记入需求清单，评估对数据库、接口、页面的影响；

- 紧急修复也要补记录；
- 不口头改表、不口头改接口；
- 每次提交说明改了什么、为什么改、怎么验证。

## 13. 开发环境与协作规则

开发规范见 [00-开发规范.md](03_开发规范/00-开发规范.md)。本节只列与开发计划相关的协作要求，提交、编码、数据库、联调的详细规则以开发规范为准。

### 13.1 分支

- `main`：可运行、可构建；
- `feature/模块名`：一个功能一个分支；
- 合并前先拉最新 `main`，解决冲突后再提交；
- 不直接 push 到 `main`（当前个人开发阶段可临时直接提交，团队协作后必须走分支）。

### 13.2 提交

提交说明必须包含三段：

1. 改了什么；
2. 为什么改；
3. 怎么验证。

模板见 [commit-template.txt](03_开发规范/commit-template.txt)，只有标题的提交视为不合格。示例：

```text
feat: 增加区域查询接口

改了什么：新增 GET /api/regions，按 parentCode 返回省、市、县。
为什么改：农户和场地要按标准区域编码保存，不能继续用自由文本。
怎么验证：分别调用省级、市级、县级请求，确认逐级返回；农户保存后能按 countyCode 查询。
关联任务：基础-02
```

### 13.3 接口与数据库

- 先改文档，再改代码；
- 数据库变更写增量 SQL，不直接改生产表；
- 接口字段变更同步前端；
- 不把密钥、真实数据提交到仓库。

### 13.4 评审

- 数据库、接口、关键业务规则由项目负责人评审；
- 代码由另一名开发或项目负责人抽查；
- 测试人员看验收标准，不只看“能点”。

## 14. 每个任务的完成定义

一个任务算完成，要同时满足：

1. 代码能构建；
2. 接口能调通，或页面能操作；
3. 验收标准逐条通过；
4. 数据库变更写了 SQL；
5. 接口文档同步；
6. 没有把密钥、真实数据提交到仓库；
7. 测试人员或项目负责人看到证据。
