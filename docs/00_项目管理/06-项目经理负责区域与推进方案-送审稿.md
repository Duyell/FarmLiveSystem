## 1. 我怎么理解这个角色

一句话：**我负责“做什么、先做什么、做成什么样”，以及需求分析、架构设计和结构设计；代码由前端开发、后端开发写，界面由 UI 设计师做，测试由测试人员做。**

### 1.1 我负责什么

- **需求分析**：梳理业务流程，列出系统功能清单，写清验收标准，控制需求变更。
- **架构设计**：确定系统架构、技术栈、模块边界、关键取舍。
- **逻辑结构设计**：功能模块怎么分、业务流程怎么走、模块之间怎么调用。
- **物理结构设计**：数据库表结构、接口结构、部署结构的设计说明。
- **优先级与阶段**：把功能分高、中、低，把项目分三个阶段。
- **进度与风险**：跟踪状态、发现偏差、登记风险、推动解决。
- **成果核验**：组织阶段验收、用户试用和交付确认。

### 1.2 我不负责什么

- 不写前端、后端代码；
- 不写测试用例，不执行测试，不判定缺陷等级；
- 不做 UI 设计，界面细节由 UI 设计师决定；
- 不展开权限与隐私的具体方案、测试用例、部署命令——这些由后续文档负责；数据库与接口的详细字段由开发实现，我负责结构设计。

### 1.3 团队 5 人怎么分工

> 按当前实际团队写，不照搬项目描述里的 6 个岗位。前端、后端各 1 名开发。

| 角色 | 人数 | 主要职责 | 关键交付 |
|---|---|---|---|
| 项目经理（我） | 1 | 需求分析、架构设计、逻辑结构设计、物理结构设计、优先级、阶段、进度与风险、验收组织 | 需求文档、架构与结构设计说明、阶段计划、验收结论 |
| 后端开发 | 1 | 后端接口、业务逻辑、数据库实现、单元测试 | 后端代码、接口、单元测试 |
| 前端开发 | 1 | 电脑管理端、手机网页、前端交互与适配 | 电脑页面、手机网页、前端代码 |
| UI 设计师 | 1 | 原型、界面设计、手机网页适配、设计规范 | 原型、页面设计、设计规范 |
| 测试人员 | 1 | 测试计划、测试用例、执行测试、跟踪缺陷 | 测试用例、测试报告、缺陷清单 |

### 1.4 谁主责、谁配合、谁验收

| 工作事项 | 主责 | 配合 | 验收 |
|---|---|---|---|
| 需求分析与优先级 | 项目经理 | 后端开发、前端开发、UI 设计师、测试人员 | 项目经理 |
| 架构与结构设计 | 项目经理 | 后端开发、前端开发、测试人员 | 项目经理 |
| 页面与交互设计 | UI 设计师 | 前端开发、项目经理 | 项目经理 |
| 前端页面开发 | 前端开发 | UI 设计师、后端开发、测试人员 | 项目经理 |
| 后端接口开发 | 后端开发 | 前端开发、测试人员 | 项目经理 |
| 测试 | 测试人员 | 前端开发、后端开发 | 项目经理 |
| 部署 | 测试人员 | 后端开发、前端开发 | 项目经理 |

### 1.5 我对自己工作的要求

- **需求上**：能拆业务流程、列全功能、写清验收标准。
- **设计上**：能画架构、逻辑结构、物理结构，能讲清为什么这样设计。
- **管理上**：能排优先级、分阶段、盯进度和风险。
- **取舍上**：不追求完美拖延，先保核心流程；项目结束能复盘。

## 2. 我怎么管需求

### 2.1 我管需求的顺序

1. **收集**：老板、客户、农户、管理员、团队提的需求，先进入需求清单，不直接进开发。
2. **分析**：梳理业务流程，判断值不值得做，拆成可开发、可验收的功能。
3. **分高、中、低**：只列可能会做的功能，按高、中、低排。
4. **评审**：开发、UI、测试一起看，确认能不能做、有没有遗漏。
5. **变更**：新需求先评估影响，再调整分级，不口头插队。
6. **跟踪**：看状态、看证据，不看“口头完成”。
7. **验收**：按验收标准逐条过，通过、待优化、不通过三档。

### 2.2 高、中、低怎么分

| 分级 | 含义 | 放在哪个阶段 |
|---|---|---|
| **高** | 缺了它，核心流程走不通，或触碰合规、安全底线 | 第一阶段核心功能 |
| **中** | 核心能跑，但体验、分析、治理明显不足 | 第二阶段功能增强 |
| **低** | 锦上添花，资源有余力再做 | 第二阶段末或有余力时 |

> 判断标准只有三条：不做会不会让主流程走不通；是不是合规、安全底线；有没有低成本替代。

### 2.4 我怎么处理“加需求”

- 先问：不做会不会影响第一阶段核心流程？会，才考虑动第一阶段；不会，进第二阶段的清单。
- 再看：是不是合规、安全底线？是，必须加；不是，排到中或低。
- 最后看：有没有低成本替代？有，先用替代方案，不急着开发。
- 无论加不加，都留一条记录：谁提的、为什么、放到哪一级、什么时候做。

### 2.5 AI 助手需求我怎么管

- **场景**：只做规则、溯源、操作指引问答；只读，不提交、不修改、不取消预约。
- **不替代**：人工审核、资源调度、纠纷处理这些关键环节，仍由人做。
- **验收**：前 5 条检索命中率不低于 85%，答案正确率不低于 80%，引用准确率不低于 90%，该拒答时拒答率不低于 85%。
- **降级**：主大模型 → 备用大模型 → 常见问题关键词 → 人工。
- **风险**：幻觉、提示词注入、外部服务不可用；必须留人工兜底，不能让人工智能越权写业务。

## 3. 我怎么分阶段

> 只分三个阶段。验收不单列阶段，放在第三阶段末尾。

| 阶段 | 目标 | 主要功能 | 我负责的设计与管理 | 团队交付 | 什么算过 |
|---|---|---|---|---|---|
| **第一阶段 核心功能** | 跑通“预约→审核→排队/候补→通知”完整流程 | 基础信息、预约提交与冲突校验、审核、我的预约、取消、排队与候补、通知、登录与角色、基础日志与脱敏、工作台、电脑管理端与手机网页核心页面 | 需求分析；架构设计；逻辑结构与物理结构设计；高优先级范围；阶段计划；进度与风险 | 需求与设计文档、数据库与接口结构说明、代码、UI 页面、测试用例与报告 | 核心流程可演示；高优先级验收标准逐条通过；没有阻断缺陷；100 并发同一时段仅 1 个成功；50 并发排队无重号；列表与日志无完整手机号；电脑和手机网页都能正常使用 |
| **第二阶段 功能增强** | 把“能用”提升到“好用、可分析、可治理、有 AI 助手亮点” | 预约调整、四项统计指标与导出、趋势图与 PDF、农户个人数据、二次验证、日志查询与防篡改、AI 助手（知识库、问答、引用、拒答、转人工、评测）、校准提醒、通知模板 | 增强功能的需求分析；AI 助手验收标准；统计口径；范围控制 | 代码、UI 页面、AI 助手服务、测试用例与报告 | 中优先级验收标准通过；回归测试通过；AI 助手指标达标；文档同步 |
| **第三阶段 测试与部署** | 证明整体可靠、安全、可复现，并完成验收 | 系统功能测试、性能测试、安全测试、兼容性与 H5 适配检查、用户试用、部署、备份恢复、验收 | 组织系统测试与用户试用；确认部署与备份；决定是否放行；组织验收 | 测试报告、部署包、备份恢复记录、验收材料 | 阻断级测试全部通过；没有遗留阻断缺陷；性能与安全达标；部署可复现；备份能恢复；用户试用通过；验收签字 |

> 测试不是第三阶段才开始。第一、二阶段每个功能都要有验收标准、自测和测试用例；第三阶段做的是系统级测试、部署和验收。

## 4. 我怎么跟需求

### 4.1 需求评审与变更

- **什么时候评**：阶段启动前、新增或变更需求时、关键设计或接口变更时、阶段验收前。
- **谁来**：我主持；后端开发、前端开发、UI 设计师、测试人员参加；老板或客户代表按需参加。
- **评什么**：目标与范围、逐条需求、优先级、验收标准、异常分支、技术可行性和风险。
- **输出什么**：需求文档、设计说明、评审结论、需要变更的变更单。
- **规矩**：没有结论的争议项不进入开发；口头结论必须写进文档。

### 4.2 进度与风险

- **看什么**：阶段、功能、优先级、负责人、状态、依赖、证据、阻塞。
- **状态只有五个**：未开始、进行中、待验证、完成、阻塞。
- **怎么盯**：按阶段看状态变化和阻塞；阶段验收看整体结果，不逐条汇报。
- **偏差怎么处理**：先识别，再定性（范围、技术、依赖、资源），然后补人、拆任务、换方案或砍中低优先级；影响阶段验收就升级到老板或客户。
- **红线**：没有证据不算完成；不允许隐瞒阻塞；不允许跳过阶段验收。

### 4.3 成果核验

- **单个功能看四样**：验收标准逐条勾选、真实演示、测试报告通过、文档同步。
- **阶段验收看整体**：核心流程能演示、该阶段的功能验收通过、没有阻断缺陷、风险有处理方案。
- **用户试用**：5–6 名同学按任务脚本试用，记录卡点和耗时；任务成功率不低于 90%，易用性评分不低于 70。
- **结论只有三档**：通过、待优化、不通过。待优化不阻断阶段验收，但要进需求清单；不通过就阻断，限期整改。

## 5. 我对技术栈与架构的理解

> 架构由我负责设计，前端开发、后端开发负责实现。团队前端、后端各 1 名开发，技术栈要稳、少而精，不引入微服务、消息队列、搜索引擎这类额外运维负担。

| 层 | 选型 | 为什么 | 代价或边界 |
|---|---|---|---|
| 前端 | Vue 3 + TypeScript；电脑管理端用 Element Plus，农户端做手机网页适配（Vant） | 电脑端和手机网页各有合适组件，农户用电脑或手机都能约 | 两套组件库，手机网页适配要单独投入时间 |
| 后端 | Java 17 + Spring Boot 3 | 事务和并发成熟，适合预约冲突、排队这类强一致场景 | 开发速度不如脚本语言 |
| 数据库 | MySQL 8 | 事务、唯一约束、团队熟悉 | 统计查询需要索引和预聚合 |
| 缓存与限流 | Redis 7 | 资源查询、排队加速、接口限流 | 只做加速，不作为事实来源 |
| 文件存储 | MinIO | 资质文件对象存储、签名访问 | 单机部署要单独备份 |
| AI 助手 | Python 服务 + Qdrant 向量库 + 大模型（DeepSeek 为主，通义千问备用） | 文档解析和检索生态好，境内合规 | 依赖外部大模型，必须做降级 |
| 部署 | 容器一键部署，单机运行 | 成本低、环境可复现 | 单点故障，需要备份和快速重建 |
| 架构 | 模块化单体 + 独立 AI 助手服务 | 团队小、强一致、少运维 | 不能水平扩展，模块边界要靠设计评审守住 |

> 前端开发负责电脑管理端和手机网页；后端开发负责 Java 接口、业务逻辑和数据库实现。
>
> 前端明确要求：电脑管理端 + **手机网页（H5）适配**；农户可以用电脑，也可以用手机，两端都能完成预约、排队、候补和查看通知，不限定只能用手机。
