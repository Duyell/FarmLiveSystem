## 1. 项目背景与问题定义

农产品直播电商存在三个结构性问题：

| 痛点 | 现状 | 本项目如何解决 |
|---|---|---|
| 农户门槛高 | 预约靠微信群/电话，规则不清、反复沟通 | 在线预约 + 自动校验 + 明确驳回理由与推荐时间 |
| 溯源信息不透明 | 资质散落、无法核验 | 资质材料加密归档、状态可查、操作全程留痕 |
| 直播资源调度难 | 设备/场地靠人盯，冲突与闲置并存 | 资源台账 + 小时级占用 + 排队候补 + 占用率统计 |

**产品定位**：不是"直播平台"，而是**助农直播的资源调度与合规管理系统**。直播本身发生在第三方平台，本系统管"谁、什么时候、用什么设备、在哪个场地、播什么"。

## 3. 范围

### 3.1 范围内（In Scope）

| 模块 | 核心内容 | 优先级 |
|---|---|---|
| 基础信息管理 | 农户/资质/设备/场地建档、脱敏、状态、查询、资源空闲 | P0 |
| 直播预约管理 | 提交、时段与冲突校验、审核、驳回、调整、取消 | P0 |
| 排队与候补 | 排队号、FIFO 顺位、候补确认、冷却期、并发一致性 | P0 |
| 通知管理 | 5 类事件、站内+短信、状态、重试、开播提醒 | P0 |
| 数据统计 | 4 项指标、多维筛选、趋势、Excel/PDF 导出 | P0/P1 |
| 权限管理 | 4 角色、接口/数据权限、审计日志、二次验证 | P0 |
| RAG 问答 | 知识库上传解析、检索问答、引用、拒答、转人工、评测 | P0 |
| 工程与交付 | 架构、库表、API、规范、测试、部署、文档 | P0 |

### 3.2 范围外（Out of Scope）——明确不做

| 不做 | 原因 | 替代 |
|---|---|---|
| 直播推流/连麦/美颜 | 属直播平台能力 | 预约单记录第三方直播间链接（可选字段） |
| 商品订单、支付、退款、物流 | 无交易资质与结算需求 | 销量手工录入/导入 |
| 身份证实名认证、人脸识别 | 合规风险高、无对接资质 | 营业执照/质检报告人工审核 |
| 反向解密/批量导出完整手机号 | 违反《个人信息保护法》最小必要原则 | 二次验证后单人查看 |
| 原生 App、小程序审核发布 | 周期与资质不允许 | H5 响应式 |
| 微服务/Kubernetes | 团队规模与工期不匹配 | 模块化单体 + Docker Compose |
| 跨境部署、多语言 | 无需求 | 简体中文 |

### 3.3 范围变更
任何新增功能先入**需求池**，由 P1 评估，P0 级范围变更须 CCB 会签（见 [P0-04](04-变更与配置管理流程.md)）。

## 5. 干系人

| 干系人 | 角色 | 关注点 | 影响力 | 管理策略 |
|---|---|---|---|---|
| 部门经理 | 项目发起人 | 进度、质量、答辩结果 | 高 | 双周汇报，里程碑签字 |
| 客户代表（模拟） | 需求方 | 是否符合实验室/县域实际 | 高 | G1/G5 评审，需求确认 |
| 农户（同学扮演） | 最终用户 | 预约是否简单、通知是否及时 | 中 | UAT 观察 + 访谈 |
| 直播管理员（同学扮演） | 关键用户 | 审核效率、资源调度 | 中 | 原型走查 + 试用 |
| 项目组 P1–P6 | 执行团队 | 任务清晰、少返工 | 高 | 每日站会、周报、看板 |
| 学院/答辩评委 | 验收方 | 完整性、规范性、创新性 | 高 | 交付物齐套、演示稳定 |

**权力-利益矩阵**：部门经理/客户代表 = 重点管理；项目组 = 重点协同；农户/管理员 = 保持告知；评委 = 保持满意。

## 6. 治理与决策机制

| 机制 | 组成 | 频率 | 职责 |
|---|---|---|---|
| 项目周会 | 全员 | 每周一 30min | 进度、风险、阻塞、下周计划 |
| 每日站会 | P1–P5 | 每日 15min | 昨天/今天/阻塞 |
| 迭代评审 | 全员 + 客户代表 | 每迭代末 60min | 演示可运行功能，收集反馈 |
| 迭代回顾 | 全员 | 每迭代末 30min | 改进 1–2 项，跟踪闭环 |
| CCB | P1/P2/P5 | 按需（≤2 工作日出结论） | 基线变更审批 |
| 质量门禁 | P1/P2/P5 | G0–G5 | 见 [P0-05](05-质量保证计划与评审门禁.md) |

**升级路径**：成员 → P1（1 个工作日内）→ 部门经理（2 个工作日）→ 客户代表（影响范围/验收时）。
