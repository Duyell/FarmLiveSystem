---

## 1. 目的与原则

- **目的**：任何变更都"有记录、有评估、有审批、有验证、可回滚"，防止口头改需求导致返工与责任不清。
- **原则**：
  1. 基线之外的新增一律走变更，**先审批后动手**；
  2. 变更必须评估"需求→设计→代码→数据→测试→工期"六面影响；
  3. 紧急变更可先处理，但 **24 小时内补单**；
  4. 变更必须有验证证据（用例、报告、截图），不接受"我觉得没问题"。

## 3. 变更分级与审批

| 级别 | 判定 | 示例 | 审批 | 时限 |
|---|---|---|---|---|
| **C1 重大** | 影响范围/验收/里程碑 | 新增模块、改排队规则、改数据模型、换技术栈 | CCB 三人会签（P1/P2/P5）+ 客户代表确认 | 2 工作日 |
| **C2 一般** | 影响单模块接口/页面/用例 | 增加筛选项、调整提示文案、改导出字段 | P1 + P2 | 1 工作日 |
| **C3 轻微** | 不影响契约与验收 | 文案、样式、日志措辞 | P1（知会 P5） | 当日 |
| **C4 紧急** | 生产阻断/安全漏洞 | 无法预约、数据泄露 | P2 先处置，24h 内补 C1/C2 单 | 立即 |

**判定口诀**：改"规则/数据/契约/范围" → C1；改"单模块行为" → C2；改"呈现" → C3；"线上坏了" → C4。

## 4. 变更流程

```text
提出（任何人） 
  → 登记（P1 录入变更台账，给 CR 编号）
  → 影响分析（P2 技术 / P5 测试 / P1 工期）
  → 定级（C1–C4）
  → 审批（CCB / P1+P2 / P1）
  → 实施（分支 feature/CR-xxx，关联 REQ）
  → 验证（用例 + 回归 + 评审）
  → 合入与发布（更新 RTM、文档版本、变更记录）
  → 关闭（P1 确认）
```

### 4.1 变更申请单模板（CR）

```markdown
## CR-YYYYMMDD-NN
- 提出人/日期：
- 变更类型：需求 / 设计 / 接口 / 数据库 / 配置 / 缺陷修复
- 变更描述（做什么，不写怎么做）：
- 变更原因（业务价值/风险）：
- 涉及 REQ / 模块 / 接口 / 表：
- 影响分析：
  - 需求：新增/修改 __ 条，是否影响基线
  - 设计：架构/库表/API 是否变更
  - 代码：前端 __ 人日，后端 __ 人日
  - 数据：是否需要迁移/兼容旧数据
  - 测试：新增/修改 __ 条用例，回归范围
  - 工期：增加 __ 人日，是否影响里程碑
- 不做的后果：
- 建议方案与备选：
- 审批结论：通过 / 驳回 / 延期（理由）
- 验证证据：
```

### 4.2 影响分析清单（六面）

| 面 | 必答问题 |
|---|---|
| 需求 | 新增还是修改？影响哪些 REQ？优先级？ |
| 设计 | 是否改架构/表/接口？是否破坏兼容？ |
| 代码 | 前后端各多少人日？是否影响关键路径？ |
| 数据 | 是否迁移？旧数据如何兼容？能否回滚？ |
| 测试 | 新增/修改哪些用例？回归范围多大？ |
| 交付 | 是否影响文档、部署、演示、验收？ |

## 5. 配置管理

### 5.1 配置项

| 配置项 | 位置 | 负责人 | 变更方式 |
|---|---|---|---|
| 源码 | Gitee `main/develop/feature/*` | P2 | PR + 评审 |
| 数据库结构 | `db/migration/V*.sql`（Flyway） | P2 | 迁移脚本，禁止手改生产 |
| 接口契约 | `docs/02_设计/04-接口设计规范.md` + OpenAPI | P2 | 契约变更需通知前后端与测试 |
| 环境配置 | `.env` / 配置中心（按环境） | P5 | 不入库明文密钥 |
| 业务参数 | `sys_config` 表 | P1/P2 | 二次验证 + 审计 + 热更新 |
| 文档 | `docs/**` | P6 | 版本 + 修订记录 |
| 部署包 | 镜像 tag + `docker-compose.yml` | P5 | 版本号与 Git tag 对应 |
| 测试资产 | `tests/**`、用例集 | P5 | 与 REQ 同步 |

### 5.2 版本号规则

`主版本.次版本.修订号`：

- **主版本**：范围/架构重大变化（本项目仅 1.0）。
- **次版本**：迭代交付（v0.1 内测、v0.5、v0.9、v1.0）。
- **修订号**：缺陷修复（v1.0.1）。

Git tag 与发布版本一致；镜像 tag = `app:v1.0.0`。

### 5.3 分支与合并（与 C3-01 一致）

- `main` 保护：仅 Release/Hotfix 合入，需 1 人评审 + CI 绿。
- `develop`：集成分支，每迭代末合入 `main` 并打 tag。
- `feature/REQ-XXX-NN-简述`：功能分支，完成后 PR 到 `develop`。
- `hotfix/xxx`：从 `main` 拉出，修复合入 `main` 与 `develop`。

## 6. 紧急变更（C4）

| 步骤 | 要求 |
|---|---|
| 1. 止血 | 回滚/下线/限流，优先恢复可用 |
| 2. 通报 | 10 分钟内在项目群通报影响与预计恢复 |
| 3. 修复 | 最小改动，P2 复核 |
| 4. 验证 | 至少覆盖故障场景 + 冒烟 |
| 5. 补单 | 24 小时内补 CR，说明根因与防复发措施 |
| 6. 复盘 | 3 日内输出复盘（5 Why + 行动项） |

**禁止**：以"紧急"为名跳过评审直接改 `main`；禁止在生产库手工改数据不留脚本。

## 8. 变更与文档同步检查

每次变更关闭前，P1 必须逐项确认：

- [ ] RTM 已更新（REQ ↔ 设计 ↔ API ↔ 表 ↔ 用例）
- [ ] SRS 修订记录已更新，版本号已升
- [ ] 接口文档/OpenAPI 已更新并通知前后端
- [ ] 数据库迁移脚本已评审，可回滚
- [ ] 用例已新增/修改，并在 CI 中执行
- [ ] 相关文档（架构/UI/安全/测试/交付）已同步
- [ ] 变更记录已通知干系人
