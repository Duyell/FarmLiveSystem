## 2. 质量策略

1. **预防优于检查**：需求阶段用 BDD 消除歧义；设计阶段用接口契约与库表评审消除返工。
2. **测试左移**：P5 在 S1 介入，用例先于/同步于开发；每个 PR 附测试证据。
3. **自动化优先**：单元测试 + API 自动化 + E2E 主流程；手工只做探索与 UAT。
4. **门禁不可绕**：G1–G5 未通过不得进入下一阶段；紧急情况需 P1 书面批准并登记风险。
5. **证据留痕**：每次评审有记录、每个缺陷有复现步骤、每个结论有数据。

## 3. 评审类型与要求

| 评审 | 时点 | 参与 | 输入 | 输出 | 通过标准 |
|---|---|---|---|---|---|
| 需求评审 | G1 | 全员+客户代表 | SRS/规则/BDD/RTM | 问题清单、签字 | P0 无歧义、AC 可判定、无漏项 |
| 设计评审 | G1 | P1/P2/P4/P5 | 架构/库表/API/安全/RAG | 评审记录 | 冲突/并发/降级/合规方案可落地 |
| 原型评审 | G1 | P1/P3/P6+用户 | 可点击原型 | 修改清单 | 主流程 ≤3 步、状态齐全 |
| 代码评审 | 每 PR | P2 + 至少 1 人 | diff | 评论/批准 | 规范、逻辑、异常、测试、注释 |
| 测试评审 | 每迭代 | P1/P2/P5 | 用例/报告 | 评审记录 | P0 覆盖、断言可判定、无假绿 |
| 交付评审 | G5 | 全员+评委 | 部署包/文档/演示 | 验收单 | 清单 100%、演示无阻断 |

### 3.1 需求评审检查表

- [ ] 每条需求有唯一 `REQ` 编号、优先级、迭代
- [ ] 每条需求有 ≥2 条可判定 AC（正常 + 异常/边界）
- [ ] 每条 P0 有 BDD 场景或明确测试方式
- [ ] 术语一致（农户/资源/时段/候补/冷却）
- [ ] 范围外内容已明确列出
- [ ] 待确认项有默认决策与截止时间
- [ ] RTM 无裸奔、无孤儿

### 3.2 设计评审检查表

- [ ] 模块边界清晰，依赖方向单一
- [ ] 冲突判定有 DB 唯一约束兜底
- [ ] 排队/候补有并发与幂等方案
- [ ] 所有外部依赖有降级链
- [ ] 敏感字段加密/脱敏/审计方案完整
- [ ] 索引覆盖核心查询，分页无全表扫描
- [ ] 接口契约含错误码、幂等、鉴权
- [ ] 部署拓扑与资源规格匹配预算

### 3.3 代码评审检查表

- [ ] 提交信息含 `REQ` 编号与 `[RED|GREEN]`
- [ ] 业务逻辑与 AC 一致，有对应单测
- [ ] 异常处理不吞错、不返回 200 掩盖失败
- [ ] 事务边界正确，无跨事务副作用
- [ ] 无硬编码密钥/地址/业务参数（走配置）
- [ ] 日志含 traceId，不打印敏感信息
- [ ] 注释解释"为什么"，复杂分支有说明
- [ ] 无 `TODO` 遗留（或已登记 Issue）

## 5. 缺陷管理

### 5.1 严重度定义

| 级别 | 定义 | 示例 | 修复时限 |
|---|---|---|---|
| **P0 致命** | 主流程阻断/数据错误/安全漏洞 | 无法预约、超卖、越权看手机号 | 24h |
| **P1 严重** | 主要功能不可用但有规避 | 候补通知不发、导出失败 | 3 天 |
| **P2 一般** | 次要功能/体验问题 | 筛选不生效、文案错误 | 本迭代 |
| **P3 轻微** | 样式/建议 | 对齐、错别字 | 下迭代 |

### 5.2 缺陷生命周期

```text
新建 → 确认（P5） → 指派（P2） → 修复中 → 待验证 → 关闭
                                  ↘ 拒绝（需理由） → 复议（P1）
                                  ↘ 延期（P1 批准，登记风险）
```

### 5.3 缺陷单必填

- 标题：`[模块] 现象 + 条件`
- 环境/版本/账号
- 复现步骤（可复制）
- 期望 vs 实际
- 证据（截图/日志/traceId/请求响应）
- 关联 REQ / 用例
- 严重度/优先级
