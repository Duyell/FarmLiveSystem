### 1.2 已实现的功能清单

**基础与权限**
- 登录（含角色选择校验）、退出、修改初始密码、令牌失效；
- 四种角色（系统管理员/直播管理员/农户/数据统计员），拦截器按路径 + 角色双重控制；
- 账号、农户、场地、设备增删改查（含手机号脱敏、删除约束、重置密码）；
- 区域字典：省/市/县逐级查询，农户/场地按标准区域编码存储与筛选。

**预约与资源**
- 农户提交预约（时段规则校验）、冲突校验（同场地同时段仅一场，小时级资源锁兜底）；
- 直播管理员审核（通过锁资源 / 驳回 + 推荐时间）、我的预约、取消（24 小时边界）；
- 可用资源查询（按县域/时段过滤）。

**排队与候补**
- 时段被占用才可排队（时段状态查询接口 + 页面引导）；
- 排队号、顺位、预计等待；取消预约自动晋升队首为候补；
- 候补确认自动分配设备并生成已通过预约；放弃/超时顺延；队列关闭；72 小时冷却。

**通知**
- 五类事件（审核结果/顺位变化/候补提醒/开播提醒/设备故障）站内 + 短信双渠道；
- 短信失败 1/5/15 分钟三次重试 + 手动重试；开播提醒幂等扫描；
- 通知模板增删改查（变量白名单校验）；我的通知按事件合并展示、已读、未读角标。

## 二、当前主要难点

### 2.1 并发资源冲突（已解决，待压测）

同一时段同一场地只允许一场直播。采用"提交时按预约表校验 + 审核通过时写小时级唯一资源锁"双保险，配合事务保证一致性。**遗留风险**：尚未做并发压测（开发计划要求 100 并发同段仅 1 成功），需在测试阶段用 JMeter 验证唯一键兜底是否可靠。

### 2.2 时间边界规则多且易错（已解决，需固化测试）

预约（提前 2 小时 / 30 天）、取消（24 小时）、排队（24 小时窗口、候选截止 = 开播前 1 小时、72 小时冷却）多组边界交织。当前以 `LocalDateTime` + 统一校验方法实现并逐一回归，**遗留风险**：跨天、服务器时区、临界秒差等场景需要固化为自动化测试用例，避免后续改动回归。

### 2.3 通知可靠性（基本解决）

短信为模拟网关，重试机制（1/5/15 分钟 + 手动重试）已实现并通过构造失败记录验证；双渠道用 `event_key` 关联实现按事件合并展示。**遗留风险**：接入真实短信网关时的签名、限流、回执处理未涉及；通知发送目前与主业务同事务，量大后需改异步（消息表 + 调度已具备改造基础）。

### 2.4 AI 模块技术选型（待启动）

AI 问答（知识库 + 引用 + 拒答）团队主力为 Java，计划采用纯 Java 方案（知识库文字入库 + 关键词/向量检索），或引入 Python 侧服务；需要评估部署成本后在本阶段末期定型，是剩余工作中不确定性最大的部分。

### 2.5 统计口径（待设计）

四项指标（场地占用率、场次、销量、成功率）依赖"场次完成标记 + 销售录入"，目前预约状态机已有 `completed`/`no_show`，但完成标记的操作入口尚未实现，统计前需先补齐。
