## 4. 脚本设计

### 4.1 JMeter 结构

```text
TestPlan
├─ User Defined Variables（host/token/资源ID）
├─ setUp Thread Group（登录取 token、准备测试数据）
├─ Thread Group: P02 浏览
│   ├─ CSV Data Set（farmerId/bookingId）
│   ├─ Transaction Controller: 列表+详情+资源
│   └─ Response Assertion（200 + code=OK + 关键字段）
├─ Thread Group: P03 提交
│   ├─ Constant Throughput Timer 1200/min
│   ├─ 随机时段/资源（冲突率可控）
│   └─ JSON Assertion（201 或 409 合法）
├─ Thread Group: P04 同段争抢
│   ├─ Synchronizing Timer（100）
│   └─ 汇总：成功数 == 1
├─ Thread Group: P06 排队
│   ├─ Synchronizing Timer（50）
│   └─ 断言 queueNo 唯一（后置 JSR223 收集）
└─ Backend Listener（InfluxDB/Prometheus，可选）
```

> 也可用 k6（`tests/perf/*.js`）——脚本更易版本化；二者选一，团队统一。

### 4.2 关键断言

- HTTP 200/201/409 符合场景预期；
- `code` 与业务状态正确；
- 响应时间断言（仅记录，不因单次超时中断）；
- 汇总报告：P50/P90/P95/P99、TPS、错误率；
- 数据校验：压测后跑对账 SQL（见 §6）。

## 6. 压测后数据对账

```sql
-- 1. 同一资源同一槽位是否存在重复有效占用
SELECT resource_type, resource_id, slot_start, COUNT(*) c
FROM resource_lock WHERE status='LOCKED'
GROUP BY 1,2,3 HAVING c > 1;               -- 期望 0 行

-- 2. 排队号是否重复
SELECT queue_no, COUNT(*) c FROM queue_ticket
GROUP BY queue_no HAVING c > 1;             -- 期望 0 行

-- 3. 同一队列顺位是否有并列（按 created_at,id 计算）
--    应用层导出快照后脚本校验，期望无重复

-- 4. 预约与占用是否一致
SELECT b.id FROM booking b
LEFT JOIN resource_lock r ON r.booking_id=b.id AND r.status='LOCKED'
WHERE b.status='APPROVED' AND r.id IS NULL; -- 期望 0 行
```

## 7. 瓶颈分析与调优

| 现象 | 可能原因 | 调优 |
|---|---|---|
| 提交 P95 高 | 唯一约束等待/锁竞争 | 缩短事务、固定锁顺序、减少槽位写入 |
| 列表慢 | 缺索引/深分页 | 联合索引、游标分页、避免 `%like%` |
| 统计慢 | 实时聚合大表 | 预聚合 `stat_daily`、从库、缓存 |
| 导出 OOM | 一次加载全量 | 流式/分页 2000、SXSSF |
| 连接池耗尽 | 慢 SQL/事务过长 | 调池、超时、慢 SQL 治理 |
| GC 频繁 | 大对象/内存泄漏 | 减小批量、堆转储分析 |
| Redis 热 key | 单资源高频 | 本地缓存/拆分 key |

**调优原则**：先索引与 SQL，再缓存，最后加机器；每次只改一个变量并复测。

## 8. 容量结论（预期）

| 资源 | 结论 |
|---|---|
| 4C8G 单机 | 支撑 200 在线/20 TPS 提交；AI 并发 10 |
| MySQL | 20 万预约/100 万日志可支撑；>500 万需归档/分区 |
| 扩容 | 应用无状态可加实例；AI 可独立升配；统计走从库 |

> 若压测不达标：优先降 AI 资源占用/远程化，再考虑升配 8C16G（需 P1 审批）。
