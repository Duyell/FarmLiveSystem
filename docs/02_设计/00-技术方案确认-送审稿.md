## 1. 结论先行

| 项 | 结论 |
|---|---|
| 架构 | 模块化单体 + 独立 AI 助手服务 |
| 前端 | 电脑管理端 + 手机网页，共用一套后端接口 |
| 后端 | Java 17 + Spring Boot 3 |
| 数据库 | MySQL 8 |
| 缓存与排队加速 | Redis 7 |
| 文件存储 | MinIO |
| AI 助手 | Python 服务 + Qdrant 向量库 + 大模型（DeepSeek 为主，通义千问备用） |
| 部署 | 单台 Linux 服务器，容器化部署，Nginx 统一入口 |
| 开发人力 | 前端 1 人、后端 1 人；不上微服务、不上消息队列、不上搜索引擎 |

**一句话**：用一套稳的、少的、前后端各一个人能维护的技术栈，先把“场地预约、排队候补、通知、统计、AI 问答”跑通。

## 2. 技术栈

| 层 | 选型 | 用途 | 为什么不用更复杂的 |
|---|---|---|---|
| 前端 | Vue 3 + TypeScript | 电脑管理端、手机网页 | 团队熟悉，组件生态全 |
| 前端组件 | Element Plus + Vant | 管理端用 Element Plus，手机网页用 Vant | 两端各有合适组件，不硬套一套 |
| 后端 | Java 17 + Spring Boot 3 | 接口、事务、权限、定时任务 | 预约冲突和排队需要强事务，Java 生态成熟 |
| 数据库 | MySQL 8 | 业务数据、预约、排队、日志 | 事务、唯一约束、团队熟悉 |
| 缓存 | Redis 7 | 排队加速、资源查询缓存、接口限流 | 只做加速，不作为事实来源 |
| 文件存储 | MinIO | 农户资质、知识库原文件 | 对象存储，部署轻，支持签名访问 |
| AI 服务 | Python + FastAPI | 文档解析、检索、问答编排；后续可扩扫描件 OCR | 文档解析和检索生态好，和 Java 后端分开 |
| 向量库 | Qdrant | 知识库文档向量检索 | 单机容器可跑，资源占用低 |
| 大模型 | DeepSeek 为主，通义千问备用 | 知识库问答 | 境内合规，成本可控 |
| 入口 | Nginx | 静态资源、反向代理、HTTPS、限流 | 单机够用，不引入网关服务 |
| 部署 | Docker Compose + 单台 Linux | 一键起服务、环境一致 | 不上 Kubernetes，团队没有运维人力 |

> 版本号在开发启动时锁定，不在本文写死小版本；以实际拉取并跑通的版本为准。

## 3. 模块划分

系统分 6 个业务模块 + 1 个 AI 助手：

| 模块 | 负责什么 |
|---|---|
| 基础信息 | 农户与资质、场地、设备、资源查询、信息更新留痕 |
| 直播预约 | 提交预约、冲突校验、审核、取消、调整 |
| 排队与候补 | 按场地排队、顺位、候补确认、放弃、超时、冷却 |
| 通知 | 五类事件、站内与短信、失败重试、模板 |
| 数据统计 | 销售录入、场地占用率、直播场次、卖出数量、预约成功率、导出 |
| 权限与审计 | 账号与角色、登录、二次验证、操作日志、日志防篡改 |
| AI 助手 | 知识库增删改查、问答、引用、拒答、转人工、评测、降级 |

前端两个入口：

- **电脑管理端**：系统管理员、直播管理员、数据统计员使用；
- **手机网页**：农户使用，也能在电脑上打开；手机网页是适配要求，不限制农户只用手机。

## 4. 关键决策

| # | 决策 | 结论 | 理由 | 代价 |
|---|---|---|---|---|
| 1 | 架构风格 | 模块化单体 + 独立 AI 服务 | 团队小，预约/排队/资源要强一致；AI 单独部署好降级 | 单体不能水平扩展，模块边界要靠评审守住 |
| 2 | 主资源 | 场地是主资源，一个场地同一时段只能一场 | 场地是直播的物理前提，先锁场地最不容易乱 | 多设备场地会闲置，后续要扩多工位再改 |
| 3 | 设备归属 | 一台设备只属于一个场地，设备表存场地编号 | 查设备、校验设备与场地一致都方便 | 设备换场地要改编号并留历史 |
| 4 | 排队维度 | 按场地 + 时段排队，确认后再分配设备 | 场地是瓶颈，按设备排队会把一个场地拆成多队 | 农户不能指定设备，只能确认后由系统分配 |
| 5 | 24 小时边界 | 开播前 24 小时内：可提交新预约，不能取消，停止候补，不能再加入排队 | 给管理员留最后的准备时间，避免临开播变来变去 | 农户临时有事不能取消，需要管理员异常处理 |
| 6 | 账号 | 系统管理员创建所有账号；直播管理员在账号上只负责农户档案和资质审核，不建账号 | 账号和业务档案分开，权限清楚 | 农户开号要等系统管理员，存在一次交接 |
| 7 | AI 边界 | AI 只读：只查知识库、回答，不写业务数据 | 防止 AI 误取消、误改预约；降低合规风险 | AI 不能帮用户直接办事，只能指路或转人工 |
| 8 | 销售数据 | 系统没有订单模块，销量由直播管理员按场次录入或导入 | 不额外做交易系统，范围可控 | 统计依赖人工录入，必须校验 |
| 9 | 部署 | 单台 Linux + 容器，Nginx 入口 | 成本低、环境一致、团队能维护 | 单点故障，必须备份和快速重建 |
| 10 | 技术克制 | 不上微服务、不上消息队列、不上搜索引擎 | 2 名开发维护不了额外中间件 | 扩展性有限，靠模块化设计弥补 |
| 11 | AI 服务语言 | Python 独立服务，保留，作为后续扫描件 OCR 的升级点 | 文档解析、OCR、评测生态好；后续可扩扫描件 | 多一门语言、多一个容器；团队主力 Java，需后端兼做；本期只做文字知识库 |

### 4.1 后续升级点

- **知识库扫描件 OCR**：本期只支持文字版 PDF、DOCX、MD、TXT；扫描件或图片 PDF 先提示暂不能解析。后续在 Python AI 服务中增加 OCR 入口，Java 业务后端不受影响。
- **本地嵌入与重排**：如果以后要求数据不出服务器，可在 Python 服务中加本地模型；Java 侧接口不变。

## 5. 数据边界

### 5.1 主要数据对象

| 对象 | 说明 |
|---|---|
| 账号 | 登录账号、角色、关联农户、账号状态、首次登录是否改密 |
| 农户 | 农户编号、姓名、县域、手机号、资质状态、资质材料 |
| 场地 | 场地编号、名称、位置、容纳人数、开放时段、状态 |
| 设备 | 设备编号、名称、型号、所属场地、状态、校准周期 |
| 预约 | 预约号、农户、场地、设备、时段、农产品清单、状态 |
| 调整申请 | 原预约、调整内容、申请原因、状态、审批意见 |
| 排队 | 排队号、农户、场地、时段、顺位、状态、候补截止时间、确认后分配的设备 |
| 通知 | 类型、渠道、内容、每个渠道的发送状态、重试次数 |
| 直播销售记录 | 预约号、农产品、规格、数量、单位、录入人、录入时间 |
| 操作日志 | 操作人、角色、时间、操作内容、网络地址、校验值 |
| 知识库文档 | 标题、类型、版本、解析状态、启停状态 |
| 问答记录 | 问题、回答、引用来源、是否转人工 |

### 5.2 关键约束

- 一个场地同一时段只能有一条有效预约；数据库唯一约束兜底，不靠代码“先查再插”。
- 一台设备同一时段只能有一条有效预约；设备必须属于预约的场地。
- 一个农户同一时段只能有一条有效预约；同一农户同一时段只能有一个有效排队。
- 一个农户只能有一个账号；账号必须关联农户。
- 同一预约同时只能有一条待审批调整。
- 销售记录只能挂在“已完成”的预约上；数量必须大于 0。
- 手机号列表和导出默认掩码；不存身份证号、家庭住址。
- 日志只能追加，不能从业务界面修改或删除。

> 详细字段、索引、外键、唯一约束组合，放在数据库设计文档；这份只确认边界。

## 6. 接口边界

接口按业务分组，不在这里列具体地址：

| 分组 | 主要做什么 |
|---|---|
| 登录与账号 | 登录、登出、改密、账号增删改查、角色分配 |
| 农户与资质 | 农户建档、资质上传、审核、查询 |
| 场地与设备 | 场地增删改查、设备增删改查、状态变更、资源查询 |
| 预约 | 提交、审核、取消、我的预约、调整申请与审批 |
| 排队与候补 | 加入排队、查顺位、确认、放弃、关闭 |
| 通知 | 站内消息、发送记录、模板、重试 |
| 统计与销售 | 销售录入、指标、筛选、导出、趋势、PDF |
| 权限与日志 | 二次验证、日志查询、日志导出、防篡改告警 |
| AI 助手 | 知识库文档增删改查、问答、引用、转人工、评测 |

三条边界：

1. **前端不直连大模型，也不直连 Qdrant**；只调后端，后端再调 AI 服务。
2. **AI 服务不直连业务库写数据**；它只读知识库，回答由后端返回给前端。
3. **文件上传走 MinIO 签名地址**，业务库只存文件标识和元数据。

## 7. 部署结构

单台 Linux 服务器，容器编排：

```text
用户浏览器
   ↓
Nginx（HTTPS、静态资源、反向代理、限流）
   ↓
前端静态文件 + 后端应用（Java）
   ↓
MySQL / Redis / MinIO
   ↓
AI 服务（Python）→ Qdrant → 外部大模型
```

| 组件 | 部署方式 | 数据卷 | 备注 |
|---|---|---|---|
| Nginx | 容器 | 证书、静态文件 | 统一入口 |
| 前端 | 静态文件 | 无 | 构建后由 Nginx 托管 |
| 后端 | 容器 | 日志 | Java 应用 |
| MySQL | 容器 | 数据卷 | 每日备份 |
| Redis | 容器 | 可持久化 | 排队和缓存 |
| MinIO | 容器 | 数据卷 | 资质和知识库文件 |
| AI 服务 | 容器 | 日志 | Python |
| Qdrant | 容器 | 数据卷 | 向量数据 |

**硬件建议**：4 核 8G 起步；如果 AI 服务、Qdrant、MySQL 都放同一台，建议 8 核 16G。磁盘按资质文件和知识库文档量预留。

**备份**：MySQL 每日全量备份；MinIO 和 Qdrant 数据卷定期备份；每季度做一次恢复演练。单机没有高可用，备份是底线。

## 8. 主要风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 单机部署 | 服务器挂了系统不可用 | 每日备份、保留重建脚本、关键数据异地备份 |
| 前端、后端各 1 人 | 人力集中在两个人身上 | 模块边界清楚、文档同步、关键逻辑评审 |
| AI 服务是 Python（为后续 OCR 预留），团队主力是 Java | 多一门语言、多一个容器，AI 进度可能拖慢 | AI 放第二阶段；本期只做文字知识库；OCR 单独排期；后端兼做或缩范围 |
| 外部大模型不可用 | AI 问答失败 | 备用模型、关键词兜底、转人工 |
| 短信网关不可用 | 通知发不出 | 站内消息兜底、失败重试、管理员提醒 |
| 没有订单模块 | 销量靠人工录入 | 录入校验、导入模板、修改留痕 |
| PDF 中文乱码 | 报表不可用 | 固定字体、生成后人工抽检 |
| 旧设计文档与当前口径冲突 | 开发和测试按错文档做 | 本文通过后统一更新旧设计文档，旧口径作废 |
